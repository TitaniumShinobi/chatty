🔥 Prime Suspects (Based on Your Stack)

1. Replit Agent Interference
	•	Replit’s “AI Agent” layer and Plan Mode can introduce aggressive memory throttling, background GC, and delayed response times especially when using:
	•	Custom environments (.replit with Nix + Node)
	•	Any persistent file reads (e.g. condition.txt, memoryStore.json)
	•	Clue: The fact that even local JSON file reads are delayed indicates filesystem or process-level choke, not Supabase.

✅ Test/Fix:
	•	Run top or htop in the Replit shell, see if a rogue process (or memory leak) is stacking.
	•	Try a fresh Replit fork with AI agents disabled (if that option exists on your account tier), and test if it loads faster with the same build.

⸻

2. Supabase Realtime / RLS Traps
	•	Your Supabase client might be initializing both auth and realtime subscriptions on load, creating:
	•	WebSocket overhead
	•	CPU spikes from RLS policy parsing
	•	Memory bloat if onAuthStateChanged() or onSnapshot() is bound to capsule memory reads
	•	This would especially lag on a mobile or Safari tab (which your screenshots show).

✅ Test/Fix:
	•	In supabase.js or your service layer, log Supabase connection time and disable Realtime for now:

createClient(SUPABASE_URL, SUPABASE_ANON_KEY, {
  realtime: { enabled: false },
})

	•	Temporarily skip RLS policies for your dev role to eliminate auth bottlenecks.

⸻

3. DigitalOcean Droplet Swap / Swapfile Usage
	•	If you’re hitting a DigitalOcean droplet and your capsule cache warmers or VVAULT syncs exceed physical memory, the system may be using swap. This is especially true during parallel capsule loads (e.g. Zen, Lin, Katana).

✅ Test/Fix:
	•	SSH into your droplet and run:

free -h
top
df -h

	•	Look for:
	•	High swap usage
	•	Disk IO spikes
	•	CPU load >1.0 on a 1-core system
	•	Add a startup throttle or serialize capsule loading.
